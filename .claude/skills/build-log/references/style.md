# 빌드 로그 글쓰기 규칙

## 포지션
- 화자: 퇴근 후 AI(클로드 코드)로 **직접 쓰는 업무 도구**를 만드는 시니어 개발자. 필명, 얼굴 없음.
- 팔지 않는다. 보여준다. 결과물(위젯·스크린샷·숫자)이 주장의 증거.
- 피할 프레임: "AI로 돈 벌기", "자동화로 월 천", "미쳤다/찐이다" 류 과장, 남의 콘텐츠 짜깁기.

## 사실 규칙 (가장 중요)
- 숫자·사건은 **collect.py 출력(커밋·diff·PR)과 README에서 확인되는 것만** 쓴다.
- 확인 안 되는 것(사용자 반응, 다운로드 수, 소요 시간 등)은 쓰지 않거나 `[확인 필요: …]` 로 표시해 사용자에게 묻는다.
- 회사 업무 사례·동료·사내 도구는 쓰지 않는다. 쓰려면 일반화("회사에서 일정 관리 툴을 고민하다가")까지만.

## 문체
- 평어체(`~했다`, `~다`). 한 줄은 짧게, 2~3줄마다 빈 줄.
- 첫 줄(훅)은 40자 이내. 피드에서 '더 보기' 전에 끝나야 한다.
- 이모지는 포스트당 0~1개. 해시태그 대신 쓰레드 주제 태그 1개.
- 코드·용어는 직장인이 알아들을 말로 한 번 번역한다 (예: "CI" → "올릴 때마다 윈도우에서 자동으로 돌려보는 검사").

## 비틀기 (니시노 원칙)
누구나 아는 말을 한 번 뒤집는다. 일반론 → 비튼 문장으로 바꾼 뒤 훅 후보에 넣는다.
- 일반론: "할 일은 눈에 보여야 한다" → "할 일 앱은 열어야 보인다. 김비서는 안 열어도 보인다."
- 일반론: "테스트는 중요하다" → "내 PC에서 되는 건 증거가 아니다. 남의 윈도우에서 돼야 증거다."

## 이야기 유형 (스토리 1개 = 유형 1개)
| 유형 | 뼈대 | 언제 |
|---|---|---|
| 계기→결과 | 불편 → 시킨 말 한 줄 → 나온 것 | 새 도구·기능 (feat) |
| 버그 사냥 | 증상 → 원인 → 한 줄 수정 → 교훈 | fix, 테스트 중 발견한 버그 |
| 결정 기록 | 고른 것 / 버린 것 / 이유 | refactor, 기술 선택 |
| 숫자로 보기 | 숫자 3개 → 의미 | 테스트 수, 지원 OS, 소요 단계 |
| 번호 리스트 | "~하는 3가지" | 여러 커밋을 묶을 때 |
| 비틀기 | 통념 → 반전 → 근거 | 어느 유형에든 훅으로 |

## 체인 구성 (1~3포스트)
1. 훅 + 상황 (왜 읽어야 하는지)
2. 본론 (무엇을/어떻게, 증거 1개)
3. 교훈 1줄 + CTA 1개 (링크는 체인 전체에서 1번, 마지막 포스트에만)
- 마지막 포스트 끝에 `[직접 쓰기: 한 문장]` 자리를 남긴다. 사용자가 자기 말로 채운다.
- 이미지 제안은 `[이미지: …]` 로 표시 (예: 위젯 스크린샷, before/after).

## CTA·링크
- 링크는 config.json 의 `links` 값만 쓴다. 없으면 `[링크 필요: 위젯 소개 페이지]`.
- 모든 링크에 UTM: `?utm_source=threads&utm_medium=social&utm_campaign=<draft-slug>-<A|B|C>`
- github.com 링크 금지(공개 레포 계정이 노출됨). 다운로드도 ayhlabs.com 페이지를 거치게.

## 훅 채점 (10점)
| 항목 | 점수 |
|---|---|
| 구체성: 숫자·고유 결과물이 있다 | 0–3 |
| 긴장/비틀기: 통념과 어긋나거나 궁금증이 남는다 | 0–3 |
| 직장인 관련성: 출근한 사람이 "내 얘기"라고 느낀다 | 0–2 |
| 간결성: 40자 이내, 군더더기 없음 | 0–2 |
7점 미만이면 다시 쓴다. 점수와 감점 이유를 초안 meta 주석에 남긴다.
